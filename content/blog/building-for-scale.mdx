About a year ago I joined a project that sounded straightforward: migrate a legacy inventory system to something modern, cloud-native, and "built for scale." Twelve months later, I've shipped the thing, it's running, and I have opinions.

This isn't a tutorial. It's closer to a post-mortem written while the memory is still fresh.

## The System

The core problem was inventory tracking across 40 warehouses in three provinces. Orders came in through an API, got routed to the nearest warehouse with stock, picked, and shipped. The old system was a monolith built on PHP and a single MySQL instance that was falling over under about 2,000 concurrent users.

The new architecture we landed on:

- **Event-driven microservices** over Kafka
- **PostgreSQL** with read replicas per region
- **Redis** for stock reservation (the hot path)
- **Next.js** frontend talking to a GraphQL gateway
- **Kubernetes** on GCP for orchestration

```
Order API → Kafka → Reservation Service → Fulfillment Service → Notification Service
                            ↓
                         Redis (stock cache)
                            ↓
                      PostgreSQL (source of truth)
```

## What Went Right

**Redis as the hot path for stock reservation** was the right call. Checking whether an item is available needs to be fast — sub-10ms fast. Hitting Postgres every time wouldn't have worked. We built a cache-invalidation layer that keeps Redis and Postgres in sync, and it has held up under 50,000 RPM during sale events.

**Event sourcing for order state** gave us an audit trail we didn't know we'd need. When a warehouse manager disputed a missed pick in month three, we could reconstruct exactly what happened at the event level. That trust saved us.

## What Went Wrong

**We over-abstracted too early.** We built a generic "workflow engine" for order state transitions because we thought we'd reuse it. We never reused it. It added two layers of indirection to every operation and made debugging significantly harder. I should have written the obvious thing first.

**Distributed transactions are genuinely hard.** Stock reservation across warehouses — where a single order might need stock from two different locations — caused us weeks of pain. We went through three designs before settling on a saga pattern with compensating transactions, and even now I think about it uneasily.

```typescript
// The saga coordinator that keeps me up at night
async function reserveMultiWarehouseStock(
  items: OrderItem[],
  warehouseIds: string[]
): Promise<ReservationResult> {
  const reservations: Reservation[] = [];

  for (const warehouseId of warehouseIds) {
    try {
      const r = await reserveAtWarehouse(warehouseId, items);
      reservations.push(r);
    } catch (err) {
      // compensate: release all previous reservations
      await Promise.all(reservations.map((r) => releaseReservation(r.id)));
      throw err;
    }
  }

  return { reservations };
}
```

## What I'd Do Differently

1. **Start monolith, extract later.** The argument for microservices at the start is mostly organizational — if you have six teams working independently. We had three engineers. A well-structured monolith with clear module boundaries would have shipped faster.

2. **Instrument from day one.** We added Grafana dashboards in month four. We should have had them in week one. Flying blind is not a valid architecture choice.

3. **Pick boring technology for the critical path.** Kafka was the right choice for the event bus, but we spent two weeks on Kafka configuration issues that a managed queue (Cloud Pub/Sub, SQS) would have handled out of the box. Save the interesting tech for the non-critical-path pieces.

## Where It Is Now

The system handles 8,000 concurrent users in production. Latency on the order creation path is p99 under 200ms. We've had two incidents, both related to Kafka consumer lag, both resolved in under an hour.

It works. I am not entirely proud of the path we took to get here, which probably means I learned something.
